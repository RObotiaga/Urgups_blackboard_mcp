# Проектирование SDK, MCP и skill

Читай при реализации клиента, инструментов MCP или инструкций агента по внутреннему веб API.

## SDK и транспорт

Раздели минимум три ответственности:

1. **Transport** отправляет запросы, ведёт cookies и редиректы, управляет соединением и таймаутами.
2. **Site protocol** восстанавливает bootstrap, вход, CSRF, формы, подписи и динамические значения.
3. **Operations** предоставляет названные пользовательские действия и возвращает предметные результаты.

Выбирай транспорт по измеренной потребности и ограничениям пользователя. Встроенный HTTP-клиент подходит, когда достаточно обычных запросов; отдельная библиотека может понадобиться для cookie jar, прокси, TLS или HTTP/2 профиля. Записывай runtime-зависимости и требуемый шаг установки. Не пытайся добиться точности транспортного отпечатка только строками User-Agent и Sec-Fetch.

Передавай в слой протокола запрос в виде метода, URL, упорядоченных пар полей, тела и контекста перехода. Это позволяет сравнить байты до отправки. Сохраняй cookies и динамические токены в рамках одной клиентской сессии. Изолируй сессии разных пользователей. Ограничивай переходы и загрузки разрешённым origin, если операция относится только к одному сайту.

Для HTML-форм бери method, action, enctype, порядок controls и скрытые значения из свежей страницы. Для multipart учитывай новую случайную boundary и реальное бинарное содержимое. Если конкретной формы не было в эталоне, общая поддержка multipart не означает подтверждённую поддержку отправки задания на данном сайте.

## MCP-инструменты

Операция MCP должна отвечать на понятную задачу пользователя: найти курс, открыть материал, прочитать уведомления, отправить форму. Не публикуй каждый низкоуровневый маршрут как отдельный инструмент без пользы для агента.

- Дай инструменту устойчивое имя, краткое описание, минимальную схему ввода и полезные подсказки для ошибок.
- Возвращай идентификатор/ссылку следующего шага, но скрывай cookies, токены и скрытые значения формы.
- Ограничивай размер ответа: длинные страницы и файлы сохраняй отдельно и возвращай путь или индекс.
- Размечай чтение и изменение. Для значимых изменений покажи план до выполнения, затем проверь ответ и текущее состояние. Учитывай повторы и частичное выполнение.
- Если endpoint заменяет список или весь объект, сначала прочитай свежее состояние, примени требуемое изменение и покажи «было → станет». После записи проверь, что остальные значения сохранились.
- Проверяй две вещи: детерминированный контракт инструмента и последовательность вызовов агента на реалистичной задаче. Изменяющий тест на живом сайте выполняй только в разрешённом объёме.

Держи список инструментов, их имена, схемы и порядок стабильными. Это облегчает использование инструмента и сохраняет повторяемость контекста; не перестраивай схемы под каждый запрос. Меняй контракт осознанно и документируй это.

## Skill и упаковка

В frontmatter skill напиши, что он делает и при каких пользовательских задачах нужен. В основном файле размести порядок выбора инструментов, проверку доступа, правила изменений и поведение при неизвестной форме. Частные маршруты, ошибки и схемы держи в references. Повторяемые детерминированные преобразования помещай в scripts, когда это реально сокращает ручную работу. Настройки и секреты держи вне SKILL.md и Git.

SDK остаётся самостоятельным модулем; MCP вызывает SDK; skill объясняет агенту, когда и как вызывать MCP. Покажи отдельные инструкции запуска для standalone MCP и плагина конкретного хоста. Если marketplace устанавливает только файлы плагина, явно опиши установку runtime-зависимостей: в проекте Blackboard пришлось выполнять npm ci отдельно.

В README перечисли поддерживаемые операции и статус их проверки. Формулируй ограничения по конкретным уровням: например, совпадает тело поиска, но отсутствует сетевой захват TLS. Отдельно укажи, какие действия доступны только по живой форме, а какие были проверены реальным ответом сайта.
