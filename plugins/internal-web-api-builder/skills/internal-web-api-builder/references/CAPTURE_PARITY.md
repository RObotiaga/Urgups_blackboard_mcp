# Захват и проверка запросов

Читай при исследовании веб-приложения, работе с HAR/CDP или заявлении о совпадении SDK-запросов с браузером.

## 1. Покрытие действий

Начни с перечня действий, доступных конкретной роли. Для каждого укажи путь в UI, результат, тип изменения и наличие официальной документации. Разделяй «видно в навигации», «запрос наблюдался» и «операция успешно повторена клиентом». Тесты, загрузки, зачисления и похожие действия могут требовать отдельного разрешения и подходящего объекта для проверки.

Используй шаблон из [assets/API_EVIDENCE_TEMPLATE.md](../assets/API_EVIDENCE_TEMPLATE.md) как файл нового проекта; заполняй его только фактами из наблюдений.

## 2. Захват цепочки

Один конечный POST редко описывает всю операцию. Зафиксируй:

- начальную страницу, вход, редиректы и установку cookies;
- переход, который открыл нужную вкладку или форму;
- источник CSRF, nonce, идентификатора курса, страницы или сессии;
- метод, URL, порядок query-полей, заголовки, content type и исходные байты тела;
- код ответа, редиректы, признаки успеха и признаки отказа.

Если HAR или CDP не сохраняет порядок wire-заголовков, версию HTTP, TLS ClientHello или тело файла, укажи «не наблюдалось». Не восстанавливай недостающие байты по отображённому в DevTools словарю заголовков.

Повтор HAR полезен как диагностический эксперимент: он показывает, какие запросы и предшествующие переходы необходимы. Сохранённые cookies, nonce и session ID быстро устаревают, поэтому рабочий SDK должен получать их заново, а не проигрывать архив как постоянный сценарий.

Запросы браузера могут содержать секреты. В публикуемом эталоне оставляй форму запроса, названия полей и безопасные статические значения. Динамический секрет описывай как источник и правило получения, не как сохранённое значение. Перед публикацией проверь URL, заголовки, тело, ответы и имена файлов на данные аккаунта.

## 3. Восстановление зависимостей

Определи цепочку получения данных: bootstrap → вход → cookies → форма/initial state → действие. Если ссылка на действие уже содержит текущие идентификаторы, извлекай её из ответа сайта. Если форма задаёт порядок и кодировку полей, сериализуй текущие controls в этом порядке. При изменении формы останови отправку и сохрани новый эталон.

Для входа по логину и паролю воспроизводи только наблюдавшуюся форму и её редиректы. Если SSO, MFA или CAPTCHA требуют участия человека, опиши этот шаг и условия продолжения сессии; не выдавай непроверенный автоматический вход за готовую функцию.

Скриптовые ответы вроде DWR разбирай как данные. Извлекай объявленную структуру допустимым парсером; не исполняй ответ сервера как JavaScript.

## 4. Уровни сравнения

Сверяй свойства раздельно. Для каждого свойства записывай результат «совпадает», «расходится», «динамическое значение» или «нет наблюдения».

| Уровень | Что сравнивать |
|---|---|
| Маршрут | Метод, origin, путь, query и порядок параметров, если он значим |
| Тело | Исходные байты, кодировка формы, порядок полей, multipart boundary и содержимое файла, когда они захвачены |
| Заголовки | Значения, наличие, регистр и порядок только если соответствующий слой действительно снят |
| Сессия | Источник cookies, CSRF, nonce, referer, redirects и срок действия |
| Транспорт | TLS fingerprint, ALPN, HTTP/2 или HTTP/3 параметры только по сетевому захвату |
| Поведение | Статус, редирект, новое состояние страницы и ошибочные сценарии |

Нормализуй для сравнения только заранее перечисленные динамические поля. Храни оригинальные байты локально во время анализа, а в репозитории — очищенный эталон или хеш там, где тело содержит данные пользователя. Если нормализация скрывает различие, сравнение не подтверждает совпадение этого поля.

## Урок Blackboard

При поиске курсов на bb.usurt.ru конечный POST оказался недостаточным источником: клиент сначала открывает актуальную вкладку «Курсы», находит живую форму и использует её action и поля. Для поиска были сопоставлены метод, URL, content type и тело. Для начального GET отдельно проверены значения браузерных заголовков. Порядок wire-заголовков и TLS не были сняты, поэтому их совпадение не заявлялось. Формы отправки файла и прохождения теста также не имели браузерного эталона и были отмечены как непроверенные.
